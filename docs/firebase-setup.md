# Firebase setup

The browser-only launcher lets Firebase provide repair hints, cloud reviews and proposed function replacements. Returned code stays data until you review and Apply it; the separate interpreter checks the current function against your fixed examples. Use a dedicated Firebase project with Firebase AI Logic and App Check. [Official web setup](https://firebase.google.com/docs/ai-logic/hybrid/web/get-started) describes supported Chrome versions, device-model availability, project setup and App Check. A generic native Prompt API does not by itself prove the hackathon's required Nano model identity.

Create `browser.local.json` outside the repository or at an ignored local path:

```json
{
  "firebaseConfig": {
    "firebase": {
      "apiKey": "YOUR_PUBLIC_FIREBASE_WEB_API_KEY",
      "projectId": "YOUR_PROJECT_ID",
      "appId": "YOUR_WEB_APP_ID"
    },
    "appCheckSiteKey": "YOUR_PUBLIC_RECAPTCHA_ENTERPRISE_SITE_KEY",
    "appName": "pit-crew-browser"
  },
  "contentSecurityPolicy": "default-src 'self'; script-src 'self' https://www.google.com/recaptcha/ https://www.gstatic.com/recaptcha/; style-src 'self'; connect-src 'self' https://content-firebaseappcheck.googleapis.com https://firebaseinstallations.googleapis.com https://firebasevertexai.googleapis.com https://www.google.com/recaptcha/; frame-src https://www.google.com/recaptcha/ https://recaptcha.google.com/recaptcha/; img-src 'none'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; form-action 'none'"
}
```

These Firebase identifiers and the enterprise site key are public configuration, not Admin credentials. Do not paste service-account keys or Gemini API secrets into this file. This CSP has supported real inference both with development tokens locally and with the normal reCAPTCHA Enterprise provider on the hosted site. That deployed check used debug mode disabled and returned a real cloud review. A complete traffic audit remains separate work; adjust only exact required origins when validating it. The default reference launcher retains its same-origin-only policy.

Restrict the browser key to the Firebase APIs you use and your intended website origins; never allow the direct Generative Language API on that public key. Firebase-enabled launches and configured static builds use `strict-origin-when-cross-origin`, so cross-origin Firebase requests carry only the page origin, without its path or query. The reference-only launcher keeps `no-referrer`. For a restricted development origin, choose a fixed port and include that origin in the key restrictions. See [Firebase's API-key guidance](https://firebase.google.com/docs/projects/api-keys).

For the current browser repair bench, the API allowlist consists of `firebasevertexai.googleapis.com`, `firebaseappcheck.googleapis.com` and `firebaseinstallations.googleapis.com`. AI Logic sends inference through the first service; App Check and Installations supply the client attestation setup. Hosting deployment uses the CLI's separate OAuth access and does not require adding the Hosting API to the public browser key. Add another service only when an implemented feature requires it, and validate the affected runtime after changing restrictions. Preserve a reviewed copy of the prior restrictions so a mistaken update can be recovered.

Before a release, read back the key's API allowlist and website restrictions through the API Keys management API, and confirm App Check enforcement through its management API. Use a deliberately invalid Installations request to verify that an approved website reaches request validation, and a deliberately invalid Identity Toolkit request to verify that an unused API is denied. These requests do not create installations, users or tokens. Separately test a real hosted cloud request with normal App Check and debug mode disabled; failed authentication probes alone cannot establish working inference. API-key restrictions identify the intended service and website usage; they do not replace App Check, authorization or quotas.

The five-request client budgets are usability limits, not server-enforced abuse protection. Review the project's live [AI Logic quotas](https://firebase.google.com/docs/ai-logic/quotas), underlying model quotas, billing plan and [production checklist](https://firebase.google.com/docs/ai-logic/production-checklist) before opening access widely. The default AI Logic per-user rate limit is 100 requests per minute; keep that distinct from this app's per-tab counts and the Gemini provider's project limits. Do not upgrade billing to work around a quota error. Limited-use App Check tokens and server-side replay protection are additional controls; baseline App Check enforcement does not imply either is enabled.

```sh
npm ci --ignore-scripts --prefix local-pit-crew/web
npm run build:firebase
npm run start:firebase -- --config /absolute/path/to/browser.local.json
```

Open the printed loopback URL in supported Chrome. Under **Runtime & setup**, **Check on-device model** calls native availability without requesting a model session or sending a repair prompt. Chrome controls its own background downloads: its [model-management guide](https://developer.chrome.com/docs/ai/understand-built-in-model-management) notes that availability checks can trigger a download shortly after a fresh profile starts when Nano-powered scam detection is active. The check therefore cannot promise that no download starts. If it reports downloadable, a separate **Download on-device model** action requests setup with native progress. This explicit download can use several GB; it sends no fixture prompt. **Stop waiting** releases the interface and requests native cancellation, but the browser may continue downloading. The wait also ends after ten minutes. Late sessions are disposed; check availability before retrying. The Firebase adapter still requires the model to report `available` before initialization. Run the baseline, read a source file, and click **Ask Nano about this failure**. This invokes Firebase AI Logic and displays its validated repair hint. The output is not a patch or correctness verdict. No coder daemon is needed for this step.

Native preparation and diagnosis each have a 90-second client wait. A timeout ends that wait, requests cancellation of the owned session and reports that no diagnosis was accepted. Check model readiness before explicitly trying again. **Close session** releases the wait immediately, even if the native provider ignores cancellation; a late result cannot reappear in a replacement run. Session cancellation does not establish that browser computation or cached model memory stopped immediately. The separate download action uses the ten-minute setup wait described above.

## Verify the installed model generation

Native `available` status and Firebase's `on_device` response label establish different facts from the installed model's generation. Neither proves Nano 4. Chrome manages the model separately from browser updates; see [Chrome's model-management documentation](https://developer.chrome.com/docs/ai/understand-built-in-model-management).

Inspect `chrome://on-device-internals` → **Broker State**. If Chrome offers to enable internal diagnostic pages, that is a separate browser setting. Record the asset name, version, ready state and selected Prompt API use case before a measured run. Do not reset, uninstall or load an arbitrary model to inspect this information. Recheck after browser/model updates, and keep the observation separate from SDK response receipts.

The first November 16, 2026 development check found `nano_v3_gpu_component` version `2025.8.8.1141` ready, while `gemma4_component` version `2026.8.7.929` was not installed. After explicitly enabling Chrome's **Gemma 4 for Built-in AI** experimental option and downloading the newer asset, a later Broker State check showed `gemma4_component` version `2026.8.7.929` ready and `prompt_api_gemma4` available. The hosted inference check used that Chrome profile and returned the expected `on_device` SDK label. Keep the visible Gemma 4 asset identity distinct from an unverified Nano 4 branding claim. The [competition's Web requirement](https://firebasehybridaihackathon.devpost.com/rules) and model identity remain a release check; browser version alone does not prove the model generation.

Chromium's [flag definition at a pinned source revision](https://chromium.googlesource.com/chromium/src/+/079ad5b81506fb387ec158e184ff95535c3b9f92/chrome/browser/flag_descriptions.h) explicitly describes this option as selecting Gemma 4 for the built-in APIs. A [separate pinned flag implementation](https://chromium.googlesource.com/chromium/src/+/ccc7d4b0c433bd7625f3ceb7b9bead978e5ede4d/chrome/browser/about_flags.cc) includes a foundational-model `model_version/v4` setting in its Gemma 4 choices. These are source-level configuration facts, not an attestation of this installed Chrome build or a confirmed Nano 4 branding mapping. Keep the required competition identity unverified until authoritative documentation or an organizer resolves that mapping.

A read-only follow-up on Chrome `157.0.8103.79` traced the installed broker manifest from Prompt API `v4` to `prompt_api_gemma4` and its low-tier GPU model. The model recipe points to `gemma4_component` version `2026.8.7.929`. That component's asset manifest identifies its base as `gemma4-2b-it` version `2026.06.10.0000`. This records the installed configuration at the time of inspection. [Chromium broker manifest format](https://chromium.googlesource.com/chromium/src/+/dc380e900e64ab32903528764caa4b339b63de50/components/optimization_guide/proto/manifest.proto)

Google's [April 2026 Android announcement](https://developer.android.com/blog/posts/announcing-gemma-4-in-the-ai-core-developer-preview) describes Gemma 4 as the foundation for Gemini Nano 4 and discusses additional Nano 4 optimizations. That Android relationship does not identify the installed Chrome component or establish its competition eligibility. The Web setup guide reviewed on November 17, 2026 describes the Chrome Prompt API and inference modes without supplying that component-to-generation mapping.

The [official Firebase workshop's web section](https://www.youtube.com/watch?v=lEsZMYkftiU&t=842s) walks through Firebase AI Logic configuration in TypeScript. Its Chrome discussion identifies built-in Gemini Nano at the model-family level. The exact Nano 4 eligibility of the component above still needs confirmation.

For local development, launch with the explicit `--app-check-debug` flag:

```sh
npm run start:firebase -- --config /absolute/path/to/browser.local.json --app-check-debug --port 59514
```

This mode is restricted to numeric HTTP loopback. A fixed, unused port preserves the local origin and its browser storage across restarts; without `--port` the server chooses an ephemeral port. The server injects a separate development bootstrap before Firebase loads, setting the SDK's debug flag to `true`. The SDK generates and persists its own private debug token; no credential is embedded in the script, public configuration or evidence export. A Firebase initialization/request logs the token in that browser's console. Follow the [App Check debug-provider guide](https://firebase.google.com/docs/app-check/web/debug-provider) to register it for the development project, then reload the same local origin. Keep it private and revoke it after testing. Never publish this development mode or its token. Normal launches omit the script and retain production attestation. Never disable App Check or domain verification to make a local test pass.

## Optional cloud opinion

The same Firebase launcher offers **Review cloud payload** after a failing reference check and a current source read. It shows the complete prompt, the Google/Firebase destination and the pinned model `gemini-3.5-flash-lite`. The standard prompt contains the original task, revision, failed check IDs, currently read source snippets and their hashes. Choose **Review second opinion with Nano hypothesis** to include the current local hypothesis. Preview sends no inference request. It excludes successful checks, event logs, connection tokens and Firebase configuration. Inspect the displayed source before sending.

**Send this prompt to Google** is a separate interaction. It consumes that exact preview once and initializes its own Firebase app and App Check provider. The browser obtains an App Check token before handing the approved prompt to Firebase AI Logic in `ONLY_IN_CLOUD` mode. A failed attestation stops the send and leaves the inference budget available. There is no automatic fallback or retry in either direction. The [Firebase inference-mode documentation](https://firebase.google.com/docs/ai-logic/hybrid/web/get-started) describes cloud-only mode and the default cloud model. No native Prompt API is required for this action, so it is usable on a browser without an available on-device model once App Check works.

Cloud failures show a bounded recovery message for a reported quota/rate limit, refused access, unavailable model or service, rejected request, timeout, unconfirmed inference source or invalid response contract. HTTP classifications use only the pinned SDK's numeric status metadata; the app does not display raw provider errors, request URLs or error bodies. A denial message lists possible setup checks rather than claiming App Check caused every denial. A quota error does not automatically retry, change billing or consume a controller proposal slot. Review a fresh prompt before explicitly sending again, or paste a replacement and continue local verification. Service-side quota reductions remain an operational change; a browser error message does not establish that any server quota was changed.

The response must cite supplied source IDs and suggest a next check. The prompt asks the model to evaluate both Nano's suspected cause and its proposed change; quoting a buggy line alone does not justify support. Actual testing has still found inconsistent classifications, so the card shows review notes and the suggested check. The raw classification remains in the run record for inspection. Treat all of this as a model opinion; actual public checks decide whether Finish opens. Editing the workspace or closing the session invalidates the preview and discards pending advice. The client limits reviews to five sends per page and a 60-second wait; these client limits do not replace project quota controls. Closing requests cancellation but cannot undo disclosure or establish that provider computation or charges stopped. Keep the project's no-cost plan; do not enable paid billing to work around quota failures.

Validation has exercised standalone cloud review and a combined Chrome on-device hint → cloud review locally with registered development tokens and on [the hosted site](https://local-pit-crew.web.app/) with the normal App Check provider and debug mode disabled. Both hosted responses returned the expected SDK inference-source labels. The cloud reviewer challenged the incorrect on-device suggestion to assign every cursor directly, citing the null/undefined absence requirement. This supports the deployed review flow, not a repair-accuracy gain. Exact Nano generation and network locality remain separate qualification work. Do not publish a development token or treat it as production attestation.

For the coding daemon path, launch `npm run start:ollama -- --config /absolute/path/to/workbench.local.json`. The JSON has exactly `ollama`, `firebaseConfig` and `contentSecurityPolicy`. `ollama` needs an explicit installed model and numeric loopback endpoint. Optional `expectedVersion`/`expectedDigest` pin identity; `contextTokens`, `maxOutputTokens`, `thinking`, `keepAliveSeconds`, `requestTimeoutMs` and `providerTimeoutMs` bound the request. Preflight does not download models. The generated patch remains unverified/in memory until a qualified runner exists.
